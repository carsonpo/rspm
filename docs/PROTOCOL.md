# RSPM Protocol — v1 (DRAFT)

Status: **draft.** The reference implementation is complete and tested, but Every constant here may change before the first
release. Once v1 ships, these rules are frozen, and any change gets a new version
string (`rspm/v2`).

This document is the normative spec. The reference implementation in [`core/`](../core/)
must match it byte for byte, and [`test/vectors/`](../test/vectors/) holds known-answer
tests for every derivation below. Read [THREAT_MODEL.md](THREAT_MODEL.md) for what the
protocol does and does not guarantee.

## 1. Design goals

1. **The storage is public.** Anyone may read and save every object in the bucket.
   This must reveal nothing beyond what is listed in §11.
2. **The server is untrusted.** The worker and bucket never see plaintext, keys,
   usernames, or which objects belong together. A malicious server can deny
   service or delete data. It cannot read, forge, or silently alter anything.
   Rollbacks are detected on devices that have seen a newer state (§6.4).
3. **Every object looks the same.** All objects are exactly 4096 bytes:
   one version byte followed by bytes that look uniformly random.
4. **No recovery.** Nothing that can decrypt a vault exists anywhere except in
   the user's head and on their Emergency Kit.
5. **Only web-standard primitives, plus a few we implement ourselves.** The
   self-implemented ones are listed in §2.2.
6. **Post-quantum.** Vault confidentiality uses only symmetric primitives with
   256-bit keys. Public-key crypto appears only in recipient sharing (§8.3) and
   is hybrid: classical plus post-quantum.

## 2. Primitives and notation

### 2.1 From WebCrypto

| Name | Use |
|---|---|
| SHA-256 | hashing, locators, PoW verification |
| HMAC-SHA-256 | locator tokens |
| HKDF-SHA-256 | all key derivation after the password KDF |
| AES-256-GCM | all symmetric encryption; 96-bit random nonce, 128-bit tag |
| X25519 | classical half of hybrid sharing |
| `crypto.getRandomValues` | all randomness |
| `CompressionStream("deflate-raw")` | vault compression before encryption |

### 2.2 Self-implemented (no WebCrypto equivalent)

| Name | Spec | Where | Use |
|---|---|---|---|
| Argon2id | RFC 9106 | `wasm/argon2.wat` (includes BLAKE2b) | password KDF |
| ML-KEM-768 | FIPS 203 | `core/mlkem.js` (includes SHA3/SHAKE) | post-quantum half of hybrid sharing |
| SHA-256 (fast loop) | FIPS 180-4 | `wasm/pow.wat` | proof-of-work search only; verification uses WebCrypto |

Each one must pass the official test vectors from its spec **and** differential
vectors generated by a reputable reference implementation at a pinned version
(see [test/README.md](../test/README.md)). If WebCrypto later ships one of these
natively and the output matches the vectors, implementations should switch to
the native version.

### 2.3 Notation

- `‖`: byte concatenation. String literals are ASCII bytes with no terminator.
- `u32be(x)`, `u64be(x)`: big-endian unsigned integers.
- `H(x)` = SHA-256(x). `HMAC(k, m)` = HMAC-SHA-256.
- `HKDF(ikm, salt, info, L)` = HKDF-SHA-256, output length `L` bytes.
- `b32(x)`: RFC 4648 base32, **lowercase**, no padding.
- `trunc16(x)`: first 16 bytes of `x`.

## 3. Credentials

A vault is opened by three secrets together:

| Secret | Chosen by | Entropy | Notes |
|---|---|---|---|
| Username `U` | user | low | Not public. Used as a salt and to separate users. |
| Password `P` | user | low–medium | Never stored. |
| Account Key `K` | **generated** at signup | 128 bits | Shown once on the Emergency Kit; may be cached on trusted devices. |

The Account Key is what makes a public bucket safe. Even a weak password combined
with an unknown 128-bit key cannot be brute-forced offline. The password protects
against theft of a device or Emergency Kit.

### 3.1 Normalization

- `U` = UTF-8 bytes of `NFKC(trim(username)).toLowerCase()`
- `P` = UTF-8 bytes of `NFC(password)` (not trimmed, case preserved)

### 3.2 Account Key encoding

```
K           = 16 random bytes
check       = trunc(H("rspm/v1/akey" ‖ K), 2 bytes)
display     = "RSPM1-" ‖ groups of 4 of uppercase b32(K ‖ check), joined by "-"
```

When reading a key, clients ignore case, whitespace, and `-`, and reject it if
the checksum fails.

### 3.3 Key derivation

```
salt    = trunc16(H("rspm/v1/salt" ‖ U))
pw_key  = Argon2id(P, salt, m = 65536 KiB, t = 3, p = 1, len = 32)
ikm     = pw_key ‖ K
loc_key = HKDF(ikm, "rspm/v1", "loc", 32)    // locators and delete tokens
enc_key = HKDF(ikm, "rspm/v1", "enc", 32)    // AES-256-GCM vault key
```

The Argon2id parameters are the minimum. 64 MiB is about the most an iOS PWA can
reliably allocate.

## 4. Objects

### 4.1 Object paths

| Prefix | Contents | Mutable? |
|---|---|---|
| `b/{locator}` | vault blocks | create-once, delete-by-token |
| `e/{hour}/{locator}` | share blocks, expiring | create-once, delete-by-token, auto-deleted after `hour` |
| `h/{locator}` | public handle records (§8.3.1) | create-once, delete-by-token |

`{locator}` is always 26 characters (`b32` of 16 bytes). `{hour}` is a decimal
Unix hour (`floor(unix_seconds / 3600)`).

### 4.2 Locators and delete tokens

Every vault or share object has a **label** (structured bytes, defined per use
below) and is located through a token:

```
t       = HMAC(key, label)                     // 32 bytes: delete token
locator = b32(trunc16(H("rspm/v1/locator" ‖ t)))
```

- Reading requires only `locator`.
- Deleting requires presenting `t`. The worker checks that it hashes to the locator.
- Neither value reveals `key`, `label`, or anything about related objects.

The worker therefore needs no per-object metadata and no accounts to authorize
deletes.

### 4.3 Block format

Every object is exactly **4096 bytes**:

```
offset  size   field
0       1      version = 0x01
1       12     nonce (random)
13      4083   AES-256-GCM(key, nonce, plaintext, aad) — 4067-byte plaintext + 16-byte tag
```

```
aad = "rspm/v1/block" ‖ locator_bytes      // the 16 raw bytes behind the locator
```

Binding the locator into the AAD means the server cannot swap one block for
another valid block.

Plaintext (4067 bytes):

```
offset  size   field
0       1      type
1       2      len (u16be), ≤ 4064
3       len    payload
3+len   …      zero padding
```

| type | meaning |
|---|---|
| `0x01` | vault head |
| `0x02` | vault data chunk |
| `0x11` | share head |
| `0x12` | share data chunk |

Exceptions to the encrypted format, each still exactly 4096 bytes starting with
`0x01`: the recipient-share key block (§8.3.2) and handle records (§8.3.1).

## 5. Vault contents

The vault plaintext is a UTF-8 JSON document:

```json
{
  "v": 1,
  "items": [
    { "id": "<b32 16B>", "type": "login", "name": "…", "updated": 1730000000,
      "url": "…", "username": "…", "password": "…", "notes": "…" },
    { "id": "…", "type": "totp", "name": "…", "updated": 0, "otpauth": "otpauth://totp/…" },
    { "id": "…", "type": "env",  "name": "my-api", "updated": 0,
      "vars": { "STRIPE_KEY": "…", "DATABASE_URL": "…" } },
    { "id": "…", "type": "note", "name": "…", "updated": 0, "body": "…" }
  ],
  "tombstones": { "<item id>": 1730000000 },
  "shares": [ { "s": "<b32 32B>", "hour": 482000, "n": 2, "created": 0 } ],
  "identity": { "handle": "…", "x25519_sk": "…", "mlkem_seed": "…" }
}
```

Item schemas are versioned with the document (`v`). Clients must keep fields
they don't recognize when they rewrite an item.

### 5.1 Serialization and padding

```
raw     = deflate-raw(UTF-8(JSON))
chunks  = raw split into 4064-byte pieces
n       = max(8, next_power_of_two(len(chunks)))
```

Chunks beyond `len(chunks)` are empty (`len = 0`). This pads every vault to 8, 16,
32, … blocks, so an observer learns only the vault's size class.

## 6. Generations

The vault is never modified in place. Each save writes a complete new
**generation** `G` (1, 2, 3, …), then deletes the previous one.

### 6.1 Labels

```
label_head(G)        = "head" ‖ u64be(G)
label_data(G, w, i)  = "data" ‖ u64be(G) ‖ w ‖ u32be(i)      // w = 16 random bytes per write attempt
```

Both use `key = loc_key`. Blocks are encrypted with `enc_key`.

### 6.2 Head payload (type `0x01`)

```json
{ "v": 1, "gen": 42, "w": "<b32 w>", "n": 8, "len": 9123, "ts": 1730000000 }
```

When reading a head, clients must check that `gen` matches the label they fetched.

### 6.3 Save (with optimistic concurrency)

To save from generation `G`:

1. Choose a random `w`. Create every `data(G+1, w, i)` block.
2. Create `head(G+1)`. **This is the commit point.** Creation is atomic and only
   succeeds if the object doesn't exist yet, so concurrent writers on different
   devices cannot both win.
3. If step 2 fails with `409`: delete your own data blocks from step 1, fetch
   the winning generation, merge (§6.6), and retry from step 1.
4. On success, delete:
   - all `data(G, w_G, i)` blocks,
   - every head in `R(G) \ R(G+1)` (§6.5).

Deletes are best-effort. A crash between steps 2 and 4 leaves a stale but
harmless generation, which the next save cleans up.

### 6.4 Rollback detection

Clients store, per vault, the highest `gen` they have ever verified (in
IndexedDB). If a later search returns a lower `gen`, the client must show a
rollback warning and must not save until the user acknowledges it. A brand-new
device has no stored state and cannot detect rollback (THREAT_MODEL R6).

### 6.5 Finding the latest generation

The bucket cannot be listed. Clients find `G` by checking which head locators
exist (`HEAD` requests). Writers keep exactly this set of heads:

```
R(G) = { G with the low j bits cleared : j = 0..63 }  ∪  { 2^k : 2^k ≤ G }
```

That is at most about 2·log₂(G) heads.

Search:

```
if !exists(head(1)): no vault
k = 0; while exists(head(2^(k+1))): k++
g = 2^k
for j = k-1 down to 0:
    if exists(head(g + 2^j)): g += 2^j
return g
```

This is correct because `g + 2^j` is in `R(G)` exactly when bit `j` of `G` is
set, and a head numbered higher than `G` has never been created. Stale heads
left by interrupted cleanups are all ≤ `G` and don't affect the result. The
search costs about 2·log₂(G) requests (about 20 for G = 1000). Clients should
start the search from their cached `gen` when they have one.

### 6.6 Merge

Merges happen per item, keyed by `id`: the higher `updated` wins, and a
tombstone wins over an item whose `updated` is less than or equal to the
tombstone's. Tombstones older than 90 days may be dropped.

## 7. Credential changes

Changing the password (or rotating the Account Key) means creating a **new
vault** under the new credentials, copying all items into it, checking that it
reads back correctly, and then deleting every block of the old vault. Old
ciphertext that someone downloaded before the deletion stays decryptable with
the old credentials (THREAT_MODEL R4).

## 8. Sharing

All shares live under `e/{hour}/…` and are deleted by the worker after `hour`
(§9.5). `hour` must be between `now + 1` and `now + 720` (30 days).

### 8.1 Share envelope

A share is protected by a 32-byte share secret `s`:

```
share_loc = HKDF(s, "rspm/v1", "share/loc", 32)
share_enc = HKDF(s, "rspm/v1", "share/enc", 32)
label_share(i) = "share" ‖ u32be(i)          // i = 0 is the head
```

Block 0 (type `0x11`) payload:

```json
{ "v": 1, "n": 1, "len": 812, "exp": 482000, "burn": false, "from": "<handle or null>" }
```

Blocks 1..n (type `0x12`) hold `deflate-raw(JSON(item))`, chunked and padded the
same way as the vault but with a minimum of 1 block. The sender stores `s` in
the vault's `shares` list so it can revoke the share early by presenting the
delete tokens.

**Burn after reading.** Anyone holding `s` can derive the delete tokens. If
`burn` is true, the recipient's client deletes the share after a successful
decrypt.

### 8.2 Link share

```
s = 32 random bytes
URL = https://rspm.link/#l1.{hour}.{b32(s)}
```

The secret travels only in the URL fragment, which browsers never send to the
server. Anyone with the link can open the share until it expires or is burned.

### 8.3 Recipient share (bound to a handle)

#### 8.3.1 Handles

A handle is an **opt-in, public** identity used for receiving shares. It is
separate from, and unrelated to, the login username.

```
handle_norm = NFKC(trim(handle)).toLowerCase(), 3–32 chars of [a-z0-9_-]
path        = h/{b32(trunc16(H("rspm/v1/handle" ‖ handle_norm)))}
t_h         = HMAC(loc_key, "handle" ‖ handle_norm)
```

The handle record is **plaintext** (it is public by design), 4096 bytes:

```
offset  size   field
0       1      version = 0x01
1       6      magic "RSPMH1"
7       32     x25519 public key
39      1184   ML-KEM-768 encapsulation key
1223    32     delete verifier = H(t_h)
1255    1      handle length L
1256    L      handle_norm
…              random padding to 4096
```

```
fingerprint = trunc(H("rspm/v1/fp" ‖ x25519_pk ‖ mlkem_ek), 20 bytes)
```

Clients show the fingerprint in groups of digits and must ask users to check it
out of band before sharing to a handle for the first time. Handles are first
come, first served. The server can substitute a handle record undetected unless
fingerprints are checked (THREAT_MODEL R7).

#### 8.3.2 Encapsulation

The sender, holding the recipient's `(x_pk, ek)`, computes:

```
(eph_sk, eph_pk) = X25519 keygen
ss_x             = X25519(eph_sk, x_pk)
(ct_k, ss_k)     = ML-KEM-768.Encaps(ek)
s = HKDF(ss_x ‖ ss_k, "rspm/v1/hybrid", eph_pk ‖ H(ct_k) ‖ x_pk ‖ H(ek), 32)
```

`ct_k` is bound by its hash because WebCrypto implementations limit HKDF
`info` to 1024 bytes.

The sender writes a **key block** at `e/{hour}/{b32(trunc16(H("rspm/v1/locator" ‖ HMAC(s, "keyblock"))))}`:

```
offset  size   field
0       1      0x01
1       32     eph_pk
33      1088   ct_k
…              random padding to 4096
```

Then it writes the envelope (§8.1) using `s`.

```
URL = https://rspm.link/#r1.{hour}.{keyblock_locator}
```

The recipient decapsulates with the secrets from their vault's `identity`,
re-derives the key-block locator from `s`, and checks that it matches the URL.
This proves the share was meant for them. A link that leaks is useless to anyone
who doesn't hold the recipient's identity keys.

## 9. Worker API

The base URL is `https://api.rspm.me` (configurable for self-hosting). Reads go
through the worker too (`GET`/`HEAD /v1/{path}`). A deployment may instead expose the
bucket on a public read-only domain and point clients there; nothing in the protocol
depends on which.

### 9.1 Endpoints

| Method | Path | Body | Success | Errors |
|---|---|---|---|---|
| `GET` | `/v1/pow` | — | `200 {"d": <bits>, "now": <unix>}` | |
| `GET`, `HEAD` | `/v1/{path}` | — | `200` + object | `404` |
| `PUT` | `/v1/{path}` | 4096 bytes | `201` | `400` size/path, `403` PoW/tag, `409` exists, `429` |
| `DELETE` | `/v1/{path}` | 32-byte token | `204` | `403` bad token, `404`, `429` |

- `GET`/`HEAD` are not rate-limited and need no PoW: anyone may read any object.
- Existence checks (`HEAD`) must never be served from a cache, because
  generation discovery (§6.5) depends on fresh answers. Clients append a random
  query string.
- `PUT` must use an atomic conditional create. Checking for existence and then
  writing is a race and is not acceptable.
- `DELETE` on `b/` and `e/` checks `trunc16(H("rspm/v1/locator" ‖ token)) == locator`.
  `DELETE` on `h/` checks `H(token)` against the record's delete verifier.
- `PUT` on `h/` checks that the magic is correct and that the handle stored at
  offset 1256 hashes to the path.
- `PUT` on `e/` checks the `hour` bounds from §8.

### 9.2 Proof-of-work (required on PUT and DELETE)

PoW stops people from using the public bucket as free storage and makes spam
cost CPU time. It is the main abuse control.

```
RSPM-PoW: {ts}.{b32(nonce)}

digest = H("rspm/v1/pow" ‖ ts_ascii ‖ " " ‖ method ‖ " " ‖ path ‖ H(body) ‖ nonce)
```

A request is valid when `digest` has at least `d` leading zero bits and
`|now − ts| ≤ 300`. Replaying a PoW gains nothing, because a PoW is bound to one
path and one body, `PUT` only creates, and `DELETE` is idempotent.

Clients search for nonces with `wasm/pow.wat`. The worker verifies with a single
WebCrypto hash. `d` starts at 18 and the operator may change it. Self-hosters
choose their own.

### 9.3 Client tag (not a security mechanism)

```
RSPM-Tag: {u32 hex}   = tag(floor(now / 30))  via wasm/tag.wat
```

`tag` is a deliberately obscure, hand-written WASM function shared by the client
and the worker, which accepts the current or previous window. It filters out
casual scripted abuse and nothing else. The function is public in this repo and
provides **zero** security. Its interface is fixed (u32 in, u32 out). Its body
can change with any release.

### 9.4 Block validity checks

A real block is AES-GCM output, so it is indistinguishable from random. The
worker therefore can't prove a block is genuine, but it **can** reject anything
that obviously isn't ciphertext, such as plaintext files, images, archives, or
zero-filled padding. On every `PUT`, the worker checks:

| # | Check | Applies to | Rejects |
|---|---|---|---|
| V1 | `len(body) == 4096` and `body[0] == 0x01` | all | wrong sizes, other formats |
| V2 | path matches `b/[a-z2-7]{26}`, `e/\d+/[a-z2-7]{26}`, or `h/[a-z2-7]{26}` | all | arbitrary keys |
| V3 | `len(deflate-raw(R)) ≥ 0.98 × len(R)`, where `R` is the region that should be random | all | anything compressible: text, JSON, uncompressed media, zeros |
| V4 | χ² of the byte histogram of `R` (255 degrees of freedom) `≤ 400` | all | skewed byte distributions, e.g. base64 or hex encodings of data |
| V5 | structure from §8.3.1 is valid; `R` = the padding region after the handle | `h/` | malformed handle records |

`R` is `body[1..4096]` for `b/` and `e/` objects. For honest random data, V3 and
V4 fail with probability well below 10⁻⁹, so honest clients effectively never
see a false rejection.

**What this cannot stop:** someone who encrypts their own data before uploading.
Such uploads pass every check by construction. They are limited by cost instead:
every 4 KiB needs its own PoW and counts against the per-IP rate limits, so
storing 1 GiB takes about 260,000 PoW solutions. The checks remove casual misuse
and the PoW makes deliberate misuse expensive. Neither makes misuse impossible,
and this document does not claim they do.

These checks run only on bytes the worker already receives. They need no keys,
log nothing, and are implemented in a single, readable function in
`worker/src/validate.js` so anyone can audit them.

### 9.5 Expiry and limits

- A worker cron job runs hourly and deletes every `e/{hour}/` prefix whose
  `hour < now_hour`.
- Per-IP rate limits apply to `PUT` and `DELETE` (worker binding or WAF rule).
- CORS: `Access-Control-Allow-Origin` is set only to the configured app origin.
  CORS restricts browsers only. Non-browser clients are governed by PoW and rate
  limits.
- Bucket listing **must** be disabled. Security does not depend on this
  (because of the Account Key), but listing would make it trivial to scrape the
  bucket.
- The worker logs nothing beyond what Cloudflare records by default (see
  THREAT_MODEL A3).

## 10. Client storage

| Data | Where | Notes |
|---|---|---|
| Account Key | IndexedDB, optional | Opt-in ("remember on this device"). Either wrapped by a passkey or security key (§10.2, recommended) or stored as is. |
| Highest seen `gen` per vault | IndexedDB | Rollback detection (§6.4). |
| Decrypted vault | memory only | Cleared on lock or timeout. |
| Password | never stored | |

### 10.1 Backup file

An encrypted export of the vault document, which only the same credentials can
restore:

```
backup_key = HKDF(enc_key_raw, "rspm/v1", "backup", 32)
file       = { "rspm_backup": 1, "nonce": b64(12 random bytes),
               "ct": b64(AES-256-GCM(backup_key, nonce, UTF-8(JSON(doc)), aad = "rspm/v1/backup")) }
```

Restoring merges the backup into the current document using the rules in §6.6.

### 10.2 Passkey-protected Account Key

The device can keep the Account Key encrypted under a secret that only a
WebAuthn authenticator releases after user verification: Touch ID, Face ID,
Windows Hello, or a FIDO2 security key such as a YubiKey. This uses the
WebAuthn **PRF** extension (CTAP2 `hmac-secret`). Nothing here involves a
server. Assertions are never sent anywhere; only the PRF output is used,
locally.

Registration:

```
rp.id           = the app's hostname
user            = { id: 16 random bytes, name: "rspm Account Key" }   // never the username
userVerification = required, residentKey = discouraged, attestation = none
prf_salt        = 32 random bytes
prf             = PRF(credential, prf_salt)          // at registration, or by a follow-up assertion
wrap_key        = HKDF(prf, "rspm/v1", "device-wrap", 32)
record          = { id, salt: prf_salt, kind, nonce, ct = AES-256-GCM(wrap_key, nonce, K, aad = "rspm/v1/device" ‖ hex(salt)) }
```

The record replaces the plaintext key in the device entry. To unlock, the
client asks for an assertion with `allowCredentials = [id]` and
`prf.eval.first = prf_salt`, then derives `wrap_key` and decrypts `K`. The AAD
binds the record to one account (via the §3.3 salt). The password is still
required: the passkey only replaces typing the Account Key on this device. If
the credential or username changes, the record is discarded rather than
falling back to storing `K` unprotected.

## 11. What an observer of the public bucket learns

- The number of objects under each prefix, and when they appeared or disappeared.
- For `e/`: each share's expiry hour.
- For `h/`: every public handle and its public keys (by design).

An observer of the bucket learns nothing about: which `b/` objects belong
together, how many vaults exist, how big any vault is, which usernames exist,
or which share belongs to whom. What the **operator** additionally learns
(IPs, timing, which objects are fetched together) is covered in THREAT_MODEL A3.

- The share payload size limit, and whether `env` items should support file-sized
  values.
- Whether we can switch to ML-KEM and Argon2 in WebCrypto once browsers ship them.
